How to play Decks Questions Privacy

The things people ask, answered without hedging.

Nothing below is aspirational. It describes what the source code does, why the project was never launched, and what you can do with it now that it is open source.

Status and basics

Is there a live version I can play?

No. DEEPER was built to completion and never launched. There is no submitted build, no store listing, no hosted server and no one maintaining it. What exists is the source in the repository, published under MIT. To play it you build the client and run the server yourself.

The postmortem and the viability assessment set out why it stopped there.

Can guests play without installing the app?

No. Every player needs the native client, guests included. The invite is a deeper://join/CODE custom-scheme link, which only resolves on a device where the app is already present. It saves typing the four character code, nothing more. There is no web target in app.json and no browser fallback: the join flow runs over a live socket.

This is the single biggest reason the product was never launched. A browser guest link would have been the cheapest way to test demand, and it was never built.

Do the same ten questions come up every time?

No. Each game draws ten at random from the hundred IDs in that deck, and the selector avoids anything the last ten games of the same deck used. Within a game there are never any repeats of an ID.

Worth being precise: every deck is 20 base prompts, each written five ways with a mechanical suffix. The 100 IDs are not 100 distinct questions, and the same base prompt can recur inside one game. The selector was written as if the pool were 100 deep.

How many people can play?

Two to eight. Three of the decks are capped at exactly two, because their questions assume there is one other person in the room: Couples, How Well Do You Know Me, and First Date.

Do we all have to be on the same wifi?

No. The reveal is synchronised by a server, not by the phones talking to each other, so people in different places can share a room as long as each phone can reach that server. You have to run that server yourself.

What if somebody's connection drops mid game?

The room waits for them instead of revealing without them, and their seat keeps its sealed answer. Reopening the app puts them back in the room on the same question. This is the most common cause of a stalled game, and it is deliberate: revealing early would let the last person read the room before answering.

Can I leave without ruining it for everyone else?

Yes. A guest who leaves takes only themselves out of the room. If the host leaves, hosting passes to the next person still connected rather than ending the game.

Money

What does it cost?

Nothing. The source is MIT licensed and nobody is selling anything. There is no price, no checkout and no listing to buy it from. If you self-host, you pay for your own Postgres, Redis and hosting.

Why is there a ten-game allowance in the code?

It was designed as a delayed freemium gate: the host spends one of ten credits per room, and a premium entitlement would remove the limit and unlock three decks. No products, API keys or webhook secrets were ever configured, so the purchase path is inert reference code.

The allowance is also bypassable. "Delete local data" clears the identity and the counter, and the new device key gets a fresh row with ten more games. Fixing it needs accounts, which would break the no-account design.

Who gets charged for a game?

Nobody, because no payments were ever switched on. In the code, only the host spends a local credit, and only once per room: games.credit_consumption_key prevents a reconnect charging the same room twice. Guests are never debited.

Are there ads?

No. src/lib/ads.ts is a console-only stub and no advertising SDK is wired up. An early version of the copy described a between-games placement that was never implemented. See the data handling notes.

Privacy and data

What happens to the answers I write?

In the code, they are held on the phone and in an encrypted room cache that expires two hours after the room is created whether or not the game finishes. They are deleted when the game ends, never written to the database, never logged and never sent anywhere. There is no answers table in the schema, which is the part that actually guarantees it.

So can someone read my answers later?

No. The cache is AES-256-GCM encrypted under a key the self-hosted server holds, and it is removed at the end of the game. If the encryption key is missing, the server refuses to store answers rather than quietly writing them in plain text, so the failure mode is a lost round rather than a leaked one.

Does it track players across apps?

No. The client generates a random string, keeps it in local storage and uses it as an account handle. It reads no IDFA, no IDFV, no Android Advertising ID, no IMEI and no MAC address. It ships no advertising or analytics SDK and declares no iOS tracking permission string. No server is operated today, so nobody is collecting these rows.

What does the code keep after a game?

Enough to stop a host charging the same room twice, and enough to count games played: display name, room membership, which reactions were tapped and when. That is deleted on a ninety day cycle. Users, entitlements and purchase rows are not deleted on a timer.

Is there an account deletion path?

No. The profile screen has a "Delete local data" action that clears the local identity and the free-game counter. It does not delete server-side rows, there is no account email and there is no operator to write to. If you self-host, erasure is your responsibility. The data handling notes cover the detail.

Is it safe for younger players?

After Dark is age gated and asks for confirmation before the room is created. The other seven decks are general audience, but none were written for children specifically and the project makes no child-directed compliance claim. Read the data handling notes for the detail.

The code itself

Which platforms does it target?

iOS and Android, built with Expo SDK 57 and React Native. There is no web target. The server is TypeScript on Node with Express and Socket.IO, backed by Postgres and Redis. app.json still carries a placeholder EAS project id, which is how you can tell no build was ever submitted.

Was it ever released?

No. There is no submitted build and no listing anywhere. Nothing on this site is a demo or a waitlist: it documents a repository that is published under MIT and not maintained.

Does it work offline?

No, and it cannot. A simultaneous reveal needs a server holding the authoritative state of the room, so the client says plainly when it cannot reach it rather than letting the room quietly drift out of sync.

Is there a scoreboard?

Only in How Well Do You Know Me?, where a point is scored each time a prediction of the other person's answer matches what they actually said. That deck is capped at two players, so groups never see a score. The how to play page covers the difference.

Something is broken. How do I report it?

You cannot, in any useful sense. The project is unmaintained and issues are not triaged. CONTRIBUTING.md says pull requests will not be merged. Fork it instead.

Can I use this in my own project?

Yes. MIT allows it with attribution. The README lists the known limitations you would inherit, and the postmortem explains the product decisions worth not repeating.

Take it, change it, ship it if you want.

The source, the research and the reasoning are all in the repository. MIT, no roadmap, no maintainer.
